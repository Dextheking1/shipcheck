ShipCheck — App Map

ShipCheck reads a public GitHub repo and reports whether it is ready to submit to a hackathon: public, license, README, planning docs, demo or live link, plus one short summary of what to fix first. Two files do all of it: public/index.html (the page) and server.js (the server). Nothing is stored.

One check, end to end

The route: follow one action

Stop 1 — the paste. In public/index.html, the form submit handler sends the raw input text to /api/check. The page does no parsing itself; when the verdicts come back, render() draws one row per check.
Stop 2 — the verdicts. In server.js, parseRepo() pulls owner/repo out of any pasted shape, and runChecks() asks the GitHub API about the repo, its root files, and its README, then builds the five rows. A GitHub 404 short-circuits here: first row FIX, the rest "Not run."
Stop 3 — the summary. The page sends the rows to /api/summary. makeSummary() in server.js asks the Pollinations text API for two or three sentences; on any failure the fallbackSummary() rule names the first failed check instead. The list never waits on this call.

To change this, start here

  • Add or change a check: add a row in runChecks() in server.js, and one line in the "What gets checked" list in public/index.html.
  • Change how the summary reads: the prompt string inside makeSummary().
  • Change the look: the single <style> block in public/index.html. There is no CSS file.
  • Run it on another port: PORT=9000 node server.js.

A practice to reuse

Write the acceptance example before the code. This build started from one concrete expected output, "DepVet passes license, README and demo, and fails planning docs naming the missing files" (prd.md > Features and Behavior). Every slice was verified against that fixture and the saved responses in test-evidence/. When the checker later passed its own repo on a localhost link it should not have counted, the fixture habit is what caught it: the detail line named the wrong evidence, so the heuristic got fixed and re-verified. Specifying the observable result first made the bug visible in one read.
